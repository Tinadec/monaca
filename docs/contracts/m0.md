# Monaca M0 — binding contract

**Status:** binding for the M0 run (stage 0 + stage 1) and for the full M0 feature build that
follows it. Every agent working in this repo follows this document. Where this document and a
task description disagree, this document wins; where this document and the approved
architecture plan (`docs/architecture.md`) disagree, the plan wins and this document is a bug.

**Authority:** `docs/architecture.md` = the approved M0–M4 architecture (Chinese, verbatim).
This file = the concrete, unambiguous instantiation of its M0 slice: names, JSON shapes, DDL,
file paths and artifact names. Nothing here may be hand-waved at implementation time — if a
name is not in this file, propose it here first.

**Versioning:** this file is edited only through a PR that also updates the code it governs.

### §2.4 Native artifact placement

`.node` binaries are **CI build artifacts**, not npm packages. `@monaca/core` declares **no**
npm platform `optionalDependencies`; `packages/core/index.js` is a hand-written CommonJS loader
that looks for `<package>/monaca-core.<tuple>.node` and fails with `MONACA_CORE_BINARY_MISSING`
telling the developer to run `bun run fetch:native`. `packages/core` is `"type": "commonjs"` on
purpose, so Node and Bun both read named exports off the generated `module.exports` assignment.

`bun run fetch:native` places:

| artifact | destination | committed? |
|---|---|---|
| server binary (win) | `.monaca/bin/monaca-server.exe` | no |
| server binary (linux) | `.monaca/bin/monaca-server` | no |
| napi `.node` (win) | `packages/core/monaca-core.win32-x64-msvc.node` | no |
| napi `.node` (linux) | `packages/core/monaca-core.linux-x64-gnu.node` | no |
| generated `index.d.ts` | `packages/core/index.d.ts` | **yes** |
| generated `index.js` | not used (see below) | no |
| `openapi.json` | `spec/openapi.json` | **yes** |
| event JSON Schemas | `spec/events/*.json` | **yes** |

The generated `index.js` is intentionally **not** produced or kept: it hardcodes a "reinstall
npm dependencies" failure message that does not apply here. `packages/core/index.js` is a
committed, hand-written CommonJS loader, and the napi invocation in package.json therefore passes
`--no-js` so a build can never clobber it:

```
napi build --release --platform --no-js --dts index.d.ts
```

It must keep exporting `Verifier`, `scopeSatisfies`, `version` via static `module.exports.X = …`
assignments (that is what makes named imports work under both Node's ESM loader and Bun).

## §3 Dev modes & commands

Three modes, exactly as plan §9. All three run the **same** acceptance script.

| mode | what runs locally | Rust artifacts / PG |
|---|---|---|
| **A local full** | server + gateway + console + auth-ui | `bun run fetch:native` pulls the CI build for the current commit. PG: `DATABASE_URL` if set (needs CREATEDB/CREATEROLE), else `embedded-postgres` downloads a real PG into `.monaca/pg` — no Docker, no admin rights |
| **B remote dev** | Vue apps only, Vite proxied to the remote gateway; `--with-gateway` also runs the local gateway for module development | `deploy-dev.yml` deploys to a VPS; needs that host plus secrets |
| **C ci only** | typechecks and TS unit tests only | push, then `bun run verify:ci` (`gh workflow run` + `gh run watch`); results and Playwright reports come from artifacts |

### §3.1 Commands (the complete list)

```
bun run dev [--mode a|b|c] [--with-gateway]
    Start the local stack for the chosen mode. First run without --mode prompts and records
    the answer in .monaca/dev.json. --with-gateway is meaningful in mode b only.

bun run fetch:native [--run <id>] [--branch <b>] [--fmt] [--dry-run]
    Download CI artifacts (see §10.6) into the destinations in §2.4.
    Default: the newest rust.yml run whose head_sha == the current commit.
    --run <id>:            a specific workflow run id.
    --branch <b>:          newest run on that branch (default: current branch).
    --fmt:                 also download the "rustfmt-patch" artifact and apply it.
    --dry-run:             print the planned gh commands and destinations, download nothing.

bun run verify:ci
    Mode C. Runs `gh workflow run rust.yml|web.yml` on the current branch, waits with
    `gh run watch`, then prints per-job conclusions and downloads artifacts into
    .monaca/reports/. Non-zero exit when any required job failed.

bun run e2e:skeleton --base-url <url>
    The single acceptance script (plan §13 / this document §12). Environment-agnostic: works
    against localhost:8080, the remote dev gateway, or CI.

bun run typecheck          bun run --filter '*' typecheck && tsc -p scripts/tsconfig.json
bun test                   bun test --pass-with-no-tests (repo-wide)
bun run build              bun run --filter '*' build
```

`bun run dev` in mode A prints the exact URLs a developer should open and refuses to start a
second copy of any child process already listening on its port.

### §4.2 napi surface (`@monaca/core`)

npm package `@monaca/core` at `packages/core`; `napi.binaryName = "monaca-core"`;
targets `x86_64-pc-windows-msvc` and `x86_64-unknown-linux-gnu`; no npm platform
`optionalDependencies`. Exact TypeScript signatures — the content of
`packages/core/index.d.ts`, regenerated by the rust.yml `codegen` job (napi-rs v3 typedef) and
committed via `bun run fetch:native`. Until the first codegen run lands, the committed file is a
hand-written placeholder with exactly these signatures:

```ts
export interface ActorChain { sub: string; act?: ActorChain }

export interface VerifiedToken {
  iss: string;
  sub: string;          // acc_… — the user, or the delegating user on an agent token
  aud: string;
  tid: string;          // ten_…
  org: string;          // org_…
  scope: string[];      // sorted, de-duplicated
  act?: ActorChain;     // present on delegated tokens only
  grantId?: string;     // grt_…, present on delegated tokens only
  jti: string;          // UUIDv7
  iat: number;          // seconds since epoch
  exp: number;
}

export interface VerifierOptions { clockSkewSecs?: number }
export interface VerifyExpectations { issuer: string; audience: string }

export declare class Verifier {
  constructor(opts?: VerifierOptions);
  setKeys(issuer: string, jwksJson: string): void;
  verifyAccessToken(token: string, expect: VerifyExpectations): VerifiedToken;
}

export declare function scopeSatisfies(granted: string[], required: string[]): boolean;
export declare function version(): string;
```

The native module performs **no I/O**: no DB, no network, no tokio runtime. Keys are pushed in
by TypeScript (`setKeys`) and cache invalidation is TypeScript's responsibility.

### §4.3 Error codes

Errors cross the napi boundary as JS `Error`s carrying a `code` property **and** a message
prefixed with the same code. `verifyAccessToken`/`setKeys` use exactly these:

| code | raised when |
|---|---|
| `MONACA_TOKEN_MALFORMED` | not a JWS, bad JSON, bad base64url, wrong segment count |
| `MONACA_TOKEN_UNKNOWN_KID` | `kid` absent from the loaded key set |
| `MONACA_TOKEN_INVALID_SIGNATURE` | signature does not verify |
| `MONACA_TOKEN_EXPIRED` | `exp` (plus skew) in the past |
| `MONACA_TOKEN_NOT_YET_VALID` | `nbf` (minus skew) in the future, or `iat` implausibly ahead |
| `MONACA_TOKEN_ISSUER_MISMATCH` | `iss` ≠ `expect.issuer` |
| `MONACA_TOKEN_AUDIENCE_MISMATCH` | neither `aud` string nor any `aud` array entry equals `expect.audience` |
| `MONACA_TOKEN_CLAIMS_INVALID` | a required claim is missing or has the wrong type |
| `MONACA_JWKS_INVALID` | JWKS is unparseable or holds no usable ES256 key |
| `MONACA_CORE_BINARY_MISSING` | (loader) no `.node` for this platform — run `bun run fetch:native` |
| `MONACA_CORE_PLATFORM_UNSUPPORTED` | (loader) platform is neither win32-x64 nor linux-x64 |

Server-side error codes use the same shape: `MONACA_` + upper snake case, documented at the
endpoint that raises them.

## §5 Data model

### §5.1 Layout

`monaca_control` (one DB) → `clusters`, `tenants`, `platform_admins`, `migration_rollup`.
`mt_<tenant_short>` (one DB per tenant):

* schema `tenant` — fixed name, **always written fully qualified** (`tenant.accounts`, …).
* schema `org_<org_short>` — one per org, **never** written qualified: resolved by
  `search_path` inside `with_org_tx`.

Identifiers are always short IDs (`[a-z0-9]{6,10}`) and always passed through `quote_ident`;
user input is never concatenated into DDL. PG role per org: `t<tenant_short>_o<org_short>`;
runtime login role `monaca_app` is a member of every org role and is created
**`WITH INHERIT FALSE`** (NOINHERIT).

Every org transaction runs:

```sql
BEGIN;
SET LOCAL search_path = org_<org_short>, tenant;   -- org first
SET LOCAL ROLE t<tshort>_o<oshort>;
-- … queries …
COMMIT;
```

`search_path` is defence in depth; the role grants are the real boundary, so a wrong
`search_path` still cannot read another org. The grants stay the real boundary **only** because
`monaca_app` is NOINHERIT: a plain `GRANT t…_o… TO monaca_app` defaults to `INHERIT TRUE`, which
hands the login role the union of every org's privileges the moment the grant runs — spike 2
(`scripts/spikes/embedded-pg.ts`) verified that a connection skipping `SET LOCAL ROLE` can then
read another org's rows, and that `WITH INHERIT FALSE` closes exactly that hole while leaving the
`SET LOCAL ROLE` path working. `MONACA_ORG_ROLE_ENFORCEMENT=1` must stay on.

### §5.2 Typed IDs

Encoded form: `<prefix>_<suffix>`. The suffix is the **TypeID v0.3 suffix encoding** of the 16
UUIDv7 bytes: treat the UUID as a 128-bit big-endian integer, prepend two zero bits (130 bits),
and emit 26 symbols of 5 bits each from the **lowercase Crockford base32** alphabet
`0123456789abcdefghjkmnpqrstvwxyz` (no `i l o u`, no padding). The first symbol is therefore
always `0`–`7`. UUIDv7 is generated in the application (`uuid` v7), never by PG.

Test vectors (both implementations must pass them):

| UUID | suffix |
|---|---|
| `00000000-0000-0000-0000-000000000000` | `00000000000000000000000000` |
| `01890a5d-ac96-774b-bcce-b302099a8057` | `01h455vb4pex5vsknk084sn02q` |
| `ffffffff-ffff-ffff-ffff-ffffffffffff` | `7zzzzzzzzzzzzzzzzzzzzzzzzz` |

`data-encoding`'s built-in base32 encodings use a different bit alignment, so the Rust side
implements this 26×5-bit loop by hand over a `u128` (≈15 lines, in `monaca-types`); TS does the
same over a `bigint`. Decoding is total: wrong length, a symbol outside the alphabet, a first
symbol above `7`, an unknown prefix, or a non-v7 version nibble is an error, never a default.

| prefix | entity | prefix | entity |
|---|---|---|---|
| `ten` | tenant | `grt` | grant |
| `org` | organization | `cli` | client (internal row id; the protocol `client_id` is a string column) |
| `acc` | account | `ses` | session |
| `agt` | agent | `evt` | audit event |
| `akey` | agent key | `dlg` | delegation |
| `apr` | approval | `int` | interaction (authorize → auth-ui handshake) |
| `key` | tenant signing key (`kid`) | | |

Primary keys are `uuid` columns holding UUIDv7. API responses always carry the **typed string**;
requests accept the typed string. Integer/`bigint` ids never appear in the public API.

**Exceptions — values that stay raw UUIDv7 strings (canonical hyphenated, no prefix):** the
token `jti` claim and the `jti` field of audit events. They are protocol values that standard
JWT tooling must handle untouched. A delegated token's agent identity in `act.sub` and its
`client_id` are the typed `agt_…` string.

### §5.4 Tenant provisioning saga

`CREATE DATABASE` cannot run inside a transaction, so provisioning is a resumable state machine.
Every step is idempotent, and the saga row is the tenant row itself (`state`).

| # | step | idempotency |
|---|---|---|
| 1 | insert `tenants` row, `state = 'provisioning'` | `ON CONFLICT (slug) DO NOTHING`, then re-read |
| 2 | `CREATE DATABASE mt_<short>` via `MONACA_ADMIN_DATABASE_URL` | tolerate "already exists" (SQLSTATE 42P04) |
| 3 | apply the **tenant** migration set to `mt_<short>` | each migration recorded in `tenant._migrations`; skip applied |
| 4 | create `tenant` schema objects, incl. `tenant.organizations` | part of step 3 |
| 5 | `state = 'active'` | `UPDATE … WHERE state = 'provisioning'` |

Failure leaves `state = 'provisioning'`; `monaca-server migrate` resumes from the lowest
incomplete step. Steps 2 and 3 take no lock on `tenants`, so a retry after a crash is safe.
`slug`, `short` and `db_name` are immutable after step 1.

### §5.5 Organization provisioning (one transaction)

```sql
BEGIN;
  -- 1. borrow a name that cannot collide, from the control-plane sequence space
  --    (org_short is derived from the new UUIDv7, never from user input)
  -- 2. schema
  CREATE SCHEMA org_<oshort>;
  -- 3. role
  CREATE ROLE t<tshort>_o<oshort> NOLOGIN;
  GRANT USAGE ON SCHEMA org_<oshort> TO t<tshort>_o<oshort>;
  GRANT USAGE ON SCHEMA tenant     TO t<tshort>_o<oshort>;
  GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA org_<oshort> TO t<tshort>_o<oshort>;
  GRANT SELECT, INSERT, UPDATE, DELETE ON tenant.accounts,
        tenant.account_identifiers, tenant.credentials, tenant.sessions TO t<tshort>_o<oshort>;
  GRANT SELECT ON tenant.organizations TO t<tshort>_o<oshort>;
  GRANT SELECT, INSERT, DELETE ON tenant.agent_directory TO t<tshort>_o<oshort>;
  ALTER DEFAULT PRIVILEGES IN SCHEMA org_<oshort>
        GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO t<tshort>_o<oshort>;
  GRANT t<tshort>_o<oshort> TO monaca_app;  -- membership only: monaca_app is NOINHERIT (§5.1),
                                            -- so this confers nothing until SET LOCAL ROLE runs
  -- 4. org migration set (template)
  -- 5. register the org
  INSERT INTO tenant.organizations (id, slug, schema_name, role_name, state, created_at)
  VALUES ($1, $2, 'org_<oshort>', 't<tshort>_o<oshort>', 'active', now());
COMMIT;
```

The org's `id` uuid is generated by the application **before** the transaction; `schema_name`
and `role_name` are derived from it, so a retried transaction of the same request is a no-op
(the whole transaction rolls back and re-runs with the same derived names). `monaca_app` itself
is created by bootstrap with `WITH INHERIT FALSE` (§5.1): the grant above is deliberately
membership-only, so an org transaction that forgets `SET LOCAL ROLE` reads nothing rather than
everything.

## §6 HTTP API

Two origins exist in dev; only `http://localhost:8080` (the gateway) is public. Base URLs below
use `{base}` = `MONACA_PUBLIC_BASE_URL`.

### §6.1 Protocol endpoints (issuer `{base}/t/{tenant}`)

| method | path | purpose |
|---|---|---|
| GET | `/t/{tenant}/.well-known/openid-configuration` | OIDC discovery |
| GET | `/.well-known/oauth-authorization-server/t/{tenant}` | RFC 8414 discovery (same document) |
| GET | `/t/{tenant}/.well-known/jwks.json` | JWKS |
| GET | `/t/{tenant}/oauth2/authorize` | authorization endpoint |
| POST | `/t/{tenant}/oauth2/token` | token endpoint |
| GET | `/t/{tenant}/interaction/{iid}` | interaction details, read by auth-ui |
| POST | `/t/{tenant}/interaction/{iid}/sign-in` | submit credentials |
| POST | `/t/{tenant}/interaction/{iid}/abort` | user cancelled |
| GET | `/healthz` | liveness; always `200` with `{"status":"ok"}` (server and gateway alike) |

Both discovery forms must return byte-identical JSON for the same tenant. The document:

```json
{
  "issuer": "http://localhost:8080/t/demo",
  "authorization_endpoint": "http://localhost:8080/t/demo/oauth2/authorize",
  "token_endpoint": "http://localhost:8080/t/demo/oauth2/token",
  "jwks_uri": "http://localhost:8080/t/demo/.well-known/jwks.json",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token", "client_credentials"],
  "code_challenge_methods_supported": ["S256"],
  "token_endpoint_auth_methods_supported": ["none", "client_secret_basic", "client_secret_post", "private_key_jwt"],
  "authorization_details_types_supported": ["monaca_grant"],
  "scopes_supported": ["openid", "profile", "email", "offline_access", "tools:read", "tools:write", "monaca:admin"],
  "subject_types_supported": ["public"],
  "id_token_signing_alg_values_supported": ["ES256"]
}
```

**Authorize** (`GET /t/{tenant}/oauth2/authorize`) — required params `response_type=code`,
`client_id`, `redirect_uri`, `scope`, `state`, `code_challenge`,
`code_challenge_method=S256`; optional `nonce`, `resource`, `prompt`, and the Monaca extension
`organization=<org slug>` (default: the account's membership in the tenant's `is_default` org,
else its oldest membership). An unknown `client_id` or unregistered `redirect_uri` is shown as an
error page and **never** redirected. Otherwise `response_type` other than `code`, a missing
`code_challenge`, or a method other than `S256` → redirect with `error=invalid_request`.
On success the server stores an interaction (`int_…`, TTL `MONACA_INTERACTION_TTL_SECS`) and
302s to `{MONACA_AUTH_UI_URL}/sign-in?tenant={tenant}&interaction={iid}`.

**Interaction API** — the auth-ui ↔ protocol-engine handshake (Hydra-style challenge, plan §7).
The interaction id is the bearer of the request, so it is high-entropy and single-use.

```
GET /t/demo/interaction/int_01h455vb4pex5vsknk084sn02q
200 {"interaction_id":"int_…","tenant":"demo","client":{"client_id":"monaca-console","name":"Monaca Console"},
     "scopes":["openid","profile","monaca:admin"],"organization":"acme","expires_at":"2026-01-01T00:10:00Z"}

POST /t/demo/interaction/int_…/sign-in   {"email":"admin@demo.localhost","password":"…"}
200 {"redirect_to":"http://localhost:5173/bff/callback?code=…&state=…"}

POST /t/demo/interaction/int_…/abort     {}
200 {"redirect_to":"http://localhost:5173/bff/callback?error=access_denied&state=…"}
```

Errors are problem+json (§6.1 end): `401 MONACA_INVALID_CREDENTIALS` (same response for an
unknown email and a wrong password), `404 MONACA_INTERACTION_NOT_FOUND`,
`410 MONACA_INTERACTION_EXPIRED`, `409 MONACA_INTERACTION_CONSUMED`, `400 MONACA_INVALID_REQUEST`.
auth-ui sends the browser to `redirect_to` with a full-page navigation.

**Token** (`POST /t/{tenant}/oauth2/token`, `application/x-www-form-urlencoded`).

* `grant_type=authorization_code` — `code`, `redirect_uri`, `client_id`, `code_verifier`.
  PKCE is mandatory; `S256` only.
* `grant_type=refresh_token` — `refresh_token`, `client_id`, optional narrower `scope`.
* `grant_type=client_credentials` — `client_id` (+ client authentication), `scope`, `resource`
  (RFC 8707), and `authorization_details` JSON array
  `[{"type":"monaca_grant","grant_id":"grt_…","resource":"…"}]` (RFC 9396).
  Every requested scope must be ⊆ the grant's scopes, else `invalid_scope`.

Client authentication: `client_secret_basic`, `client_secret_post`, or `private_key_jwt`
(§7.4). A `client_id` that names an **agent** (`agt_…`) authenticates with `private_key_jwt`
only, against the agent's registered `agent_keys`. Success response:

```json
{
  "access_token": "eyJ…",
  "token_type": "Bearer",
  "expires_in": 300,
  "scope": "tools:read"
}
```

`scope` is the space-delimited granted set. `refresh_token` appears only for
`authorization_code` when the request asked for `offline_access`; `id_token` only for
`authorization_code`. A `client_credentials` response never carries `refresh_token`.
Token errors follow **RFC 6749 §5.2** exactly —
`{"error":"invalid_request|invalid_client|invalid_grant|unauthorized_client|unsupported_grant_type|invalid_scope","error_description":"…"}`
with status 400 (401 for `invalid_client`, plus `WWW-Authenticate: Basic realm="monaca"`).
Everywhere else in the API, errors are **RFC 9457** `application/problem+json`:

```json
{ "type": "https://monaca.dev/errors/grant_revoked", "title": "Grant revoked",
  "status": 409, "detail": "grant grt_… was revoked at 2026-01-01T00:00:00Z",
  "instance": "/v1/orgs/acme/grants/01920000-…", "monaca_error_code": "MONACA_GRANT_REVOKED" }
```

### §6.2 `/v1` management API

Authentication: `Authorization: Bearer <access token>` whose `aud` is the management resource
`{base}/v1` and whose `scope` contains `monaca:admin`. Two ways to obtain one:

* **Console (BFF):** the signed-in user's own token from the `authorization_code` flow,
  requested with `resource={base}/v1`. The server grants `monaca:admin` only to accounts with
  `is_tenant_admin = true`; for anyone else the scope is silently dropped (RFC 6749 §3.3).
* **Automation / e2e:** the seeded confidential client `monaca-admin` via `client_credentials`
  with `client_secret_basic`. Its tokens use `sub = cli_…` and the tenant's default org.

Missing or invalid token → 401 + `WWW-Authenticate: Bearer`; valid but under-scoped →
**403** + `WWW-Authenticate: Bearer error="insufficient_scope", scope="monaca:admin"`.
All bodies are JSON; all ids are typed strings.

The tenant is the token's `tid`; `{org}` is an org **slug** in that tenant, so no `/t/{tenant}`
prefix appears under `/v1`. A resource outside the caller's tenant is **404**, not 403 —
existence is not disclosed.
An **agent** holding a delegated `monaca:admin` token is refused on `/v1/*`: those endpoints
require a `monaca:admin` token with **no `act` claim**.

```json
  "created_at": "…", "revoked_at": null }], "created_at": "…" }

// grant
{ "id": "grt_…", "org": "acme", "agent_id": "agt_…", "account_id": "acc_…",

{ "seq": 7, "id": "evt_…", "at": "…", "action": "tool.invoked", "actor_chain": [ … ],

```

Validation rules enforced by the server: `scopes` non-empty and each matches
`^[a-z][a-z0-9_.-]*(:[a-z][a-z0-9_.-]*)*$`; `resource` is an absolute `http(s)` URL; the grant's
`account_id` must be a member of `{org}`; the agent's `owner_account_id` must be a member of
`{org}`; `public_jwk` must be an EC P-256 public key (`kty=EC`, `crv=P-256`, no `d`) — a JWK
with a private component is **rejected** (`400 MONACA_PRIVATE_KEY_SUBMITTED`), so a careless
client can never leak a private key into the database.

## §7 Token formats

All tokens are JWS compact, `alg = ES256`, signed with the tenant's active `signing_keys` row;
`kid` is that row's `id`. Every token header carries `"typ"`.

### §7.1 User access token

Header `{"alg":"ES256","kid":"<uuid>","typ":"at+jwt"}`; claims:

```json
{
  "iss": "http://localhost:8080/t/demo",
  "sub": "acc_00000000000000000000000000",
  "aud": "http://localhost:8080/mcp/demo",
  "tid": "ten_00000000000000000000000000",
  "org": "org_00000000000000000000000000",
  "scope": ["tools:read"],
  "jti": "01920000-0000-7000-8000-000000000000",
  "iat": 1767225600,
  "exp": 1767226500
}
```

### §7.2 Agent-delegated token

Same, plus `act` and `grant_id`, with `sub` remaining the **delegator account**:

```json
{
  "iss": "http://localhost:8080/t/demo",
  "sub": "acc_00000000000000000000000000",
  "aud": "http://localhost:8080/mcp/demo",
  "tid": "ten_00000000000000000000000000",
  "org": "org_00000000000000000000000000",
  "scope": ["tools:read"],
  "act": { "sub": "agt_00000000000000000000000000" },
  "grant_id": "grt_00000000000000000000000000",
  "jti": "01920000-0000-7000-8000-000000000001",
  "iat": 1767225600,
  "exp": 1767225900
}
```

TTL is fixed at **300 s** and is not configurable. `scope` is the intersection of the grant's
scopes and the requested scopes: **never a union**, `aud` only narrows, `exp` only shortens
(plan §5). Multi-hop nesting (`act.act`) is M3; the verifier must already handle arbitrary depth.

### §7.3 id_token

Header `{"alg":"ES256","kid":"…","typ":"JWT"}`; claims `iss`, `sub` (account id), `aud`
(client_id), `tid`, `org`, `iat`, `exp`, `nonce` (echoed when the authorize request supplied
one). M0 issues `email` and `name` only for `scope` containing `email`/`profile`. No `at_hash`
in M0 (nothing consumes it yet); M1 adds `nonce` enforcement and `at_hash`.

### §7.4 Client assertion (`private_key_jwt`)

`client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`,
`client_assertion=<JWT>`. Required claims: `iss` **and** `sub` both equal the `client_id`;
`aud` equal to the **token endpoint URL exactly** (`http://localhost:8080/t/demo/oauth2/token`);
`exp` ≤ `iat` + 300 s; `jti` present and **single-use** (replay → `invalid_client`). Signature
verified against the client's registered JWKS (for a client) or the agent's registered
`agent_keys` (for an agent acting as a client). An assertion that is valid but not permitted for
the requested grant → `invalid_grant`; a bad signature → `invalid_client`.

## §8 Audit

### §8.1 Event JSON

```json
{
  "id": "evt_00000000000000000000000000",
  "at": "2026-01-01T00:00:00.000Z",
  "action": "agent.token.issued",
  "actor_chain": [
    { "type": "account", "id": "acc_00000000000000000000000000" },
    { "type": "agent",   "id": "agt_00000000000000000000000000" }
  ],
  "subject": { "type": "grant", "id": "grt_00000000000000000000000000" },
  "decision": "allow",
  "grant_id": "grt_00000000000000000000000000",
  "jti": "01920000-0000-7000-8000-000000000001",
  "payload": { "scope": ["tools:read"], "aud": "http://localhost:8080/mcp/demo" }
}
```

Rules: `actor_chain` is ordered outermost-first and is **never empty**; `decision` is
`allow` | `deny` | `info`; `payload` is an object (never an array, never `null`); `at` is
millisecond precision UTC. The stored form adds `seq`, `prev_hash` and `hash` (§5.7); those three
are **excluded** from the canonical bytes (§8.2) — everything else in this object is included
verbatim, so the JSON Schema in `spec/events/` is exactly this object minus those three keys.

`subject_type`/`subject.id` come from the `subject` object: `subject.type` ∈
`account` | `org` | `agent` | `agent_key` | `grant` | `client` | `tool` | `session` | `tenant`;
`subject.id` is the typed id string (a tool name stays a bare string). `action` is a dotted
lowercase verb, and the M0 set is fixed:
`account.created`, `org.member.added`, `agent.created`, `agent.key.registered`,
`agent.key.revoked`, `grant.created`, `grant.revoked`, `agent.token.requested`,
`agent.token.issued`, `agent.token.denied`, `tool.invoked`, `tool.denied`,
`interaction.sign_in.succeeded`, `interaction.sign_in.failed`. Adding an action means editing
this list and the JSON Schema in `spec/events/`.

### §8.2 Canonicalization and hashing

Canonical bytes are **RFC 8785 (JCS)** of the event object, serialized over the event exactly as
stored minus chain fields (`prev_hash`, `hash`, `seq`). The digest:

```
hash = hex(sha256(prev_hash_bytes || jcs_bytes))
```

* `prev_hash_bytes` is the raw 32-byte previous hash (NOT its hex string).
* `jcs_bytes` is the UTF-8 JCS output (no trailing newline).
* Genesis `prev_hash` is 64 zero hex characters (32 zero bytes).
* `hash` in the API is always **lowercase hex, 64 characters**.

Rust: `serde_jcs` for canonicalization, `sha2` for the digest.

### §8.3 Append

Inside the same transaction as the business write:

```sql
SELECT seq, hash FROM <schema>.audit_chain_head WHERE singleton FOR UPDATE;  -- serializes the org
INSERT INTO <schema>.audit_events (…, prev_hash, hash) VALUES (…);
UPDATE <schema>.audit_chain_head SET seq = <new seq>, hash = <new hash>, updated_at = now()
       WHERE singleton;
```

The `FOR UPDATE` on the single head row serializes audit appends per org. M0 accepts this
contention; M3 replaces it with batched Merkle sealing (plan §12.5). Chain fields are computed
by Rust, never by a trigger — the append path must be identical from the server and from tests.

### §8.4 Verification

Computed independently of the stored chain: for each row in ascending `seq`, recompute
`hash` from the recomputed `prev_hash` and the row's JCS event; compare against the stored
`hash`. The first mismatch stops the walk.

```json
{
  "valid": false,
  "checked": 17,
  "head": { "seq": 42, "hash": "3f…" },
  "first_broken": { "seq": 18, "expected": "9a…", "actual": "b2…", "reason": "hash_mismatch" }
}
```

`reason` ∈ `hash_mismatch` | `prev_hash_mismatch` | `seq_gap` | `head_mismatch`. `valid: true`
requires `checked == head.seq - from + 1` and the recomputed head hash to equal the stored head.

## §9 Gateway

Hono on Bun. Route table (order matters; the dev proxy is registered last):

| method | path | behaviour |
|---|---|---|
| GET | `/healthz` | `{"status":"ok","service":"monaca-gateway"}` |
| GET | `/bff/login` | 302 to `{public}/t/{tenant}/oauth2/authorize` with `code_challenge` (PKCE, S256), `state`, `nonce` |
| GET | `/bff/callback` | exchange `code` at the token endpoint, store tokens server-side, set the session cookie, 302 to `MONACA_CONSOLE_URL` |
| POST | `/bff/logout` | delete session, clear cookie, 204 |
| GET | `/bff/session` | `{"authenticated":true,"account_id":"acc_…","email":"…","tenant":"demo","orgs":[{"slug":"acme","role":"admin"}]}` |
| ANY | `/bff/api/*` | rewrite to `{MONACA_SERVER_URL}/v1/*`, attaching the session's bearer token; refresh it first when it expires within 30 s; 401 problem+json when there is no session |
| ANY | `/mcp/demo` | the demo MCP resource server (`@monaca/mcp` guard + `@monaca/module-mcp-demo`) |
| ANY | `/t/*`, `/.well-known/*`, `/v1/*` | dev proxy → `MONACA_SERVER_URL`, only when `MONACA_DEV_PROXY=1`. `/internal/*` is **never** proxied |

**BFF session cookie.** `__Host-monaca_session` in production; `monaca_session` when the origin
is plain `http://localhost` (browsers reject `__Host-` without `Secure`). Attributes: `HttpOnly`,
`SameSite=Lax`, `Path=/`, `Secure` in production only. Access and refresh tokens live in
gateway memory (M0) and are **never** sent to the browser.

**RFC 9728 Protected Resource Metadata.** For the demo resource:

* `GET /.well-known/oauth-protected-resource/mcp/demo` →
  `{"resource":"http://localhost:8080/mcp/demo","authorization_servers":["http://localhost:8080/t/demo"],"scopes_supported":["tools:read","tools:write"],"bearer_methods_supported":["header"]}`
* `GET /mcp/demo` without a token → 401 with
  `WWW-Authenticate: Bearer resource_metadata="http://localhost:8080/.well-known/oauth-protected-resource/mcp/demo"`
  and additionally `error="invalid_token"` when a token was presented but rejected.

**401 / 403 formats (exact).**

```
401  WWW-Authenticate: Bearer resource_metadata="http://localhost:8080/.well-known/oauth-protected-resource/mcp/demo"
403  WWW-Authenticate: Bearer error="insufficient_scope", scope="tools:write", resource_metadata="http://localhost:8080/.well-known/oauth-protected-resource/mcp/demo"
```

The 403 body is `application/problem+json` with `monaca_error_code: "MONACA_INSUFFICIENT_SCOPE"`.

**Tool → scope map (fixed for M0).**

| tool | required scope |
|---|---|
| `list_notes` | `tools:read` |
| `delete_note` | `tools:write` |

Every tool invocation is written to `/internal/audit` as `tool.invoked` (or `tool.denied` on a
scope failure) **before** the response is returned; a failure to write audit fails the request.

## §10 CI

Design rule: **pass artifacts within one workflow run** via `needs:` + `upload-artifact` /
`download-artifact`. No `workflow_run` chains — they make the feedback loop longer and the
artifact provenance murkier.

### §10.1 `rust.yml`

Trigger: `push` to `main`, `pull_request`, `workflow_dispatch`. Every job uses
`Swatinem/rust-cache` and a `paths` filter so TS-only changes skip Rust.

| job | runner | what it does | artifacts |
|---|---|---|---|
| `check` | ubuntu-latest | `cargo fmt --all` (writes, never `--check`), patch upload; then `cargo clippy --workspace --all-targets` | `rustfmt-patch` (only when the tree was not formatted) |
| `test` | ubuntu-latest | `services: postgres:18`; `cargo nextest run --workspace` | — |
| `build (windows)` | windows-latest | `cargo build --release -p monaca-server --target x86_64-pc-windows-msvc`; `napi build --release --platform --target x86_64-pc-windows-msvc` | `server-x86_64-pc-windows-msvc` → `monaca-server.exe`; `binding-x86_64-pc-windows-msvc` → `monaca-core.win32-x64-msvc.node` |
| `build (linux)` | ubuntu-latest | same for `x86_64-unknown-linux-gnu` | `server-x86_64-unknown-linux-gnu` → `monaca-server`; `binding-x86_64-unknown-linux-gnu` → `monaca-core.linux-x64-gnu.node` |
| `codegen` | ubuntu-latest | `napi build --release --dts` then `monaca-server openapi > spec/openapi.json`; regenerates `spec/events/*.json` | `codegen` → `index.d.ts`, `openapi.json`, `events/` |
| `e2e` | ubuntu-latest | `needs: [build (linux), codegen]`; stage 0 = start the server from the `server-x86_64-unknown-linux-gnu` artifact and `curl /healthz`; stage 1 = `bun scripts/e2e/skeleton.ts` | `e2e-report` → `.monaca/reports/skeleton.json` |

**rustfmt is non-fatal on branches, fatal on `main`.** Local machines have no Rust toolchain, so
contributors cannot run `cargo fmt` before pushing. `check` therefore runs `cargo fmt --all`,
uploads the diff as `rustfmt.patch`, and only fails when the ref is `refs/heads/main`:

```yaml
- run: cargo fmt --all
- run: |
    if git diff --quiet; then
      echo "formatted=0" >> "$GITHUB_OUTPUT"
    else
      echo "formatted=1" >> "$GITHUB_OUTPUT"
      git diff > rustfmt.patch
    fi
  id: fmt
- if: steps.fmt.outputs.formatted == '1'
  uses: actions/upload-artifact@v4
  with: { name: rustfmt-patch, path: rustfmt.patch, retention-days: 14 }
- if: steps.fmt.outputs.formatted == '1' && github.ref == 'refs/heads/main'
  run: |
    echo "::error::rustfmt produced changes; fix them with: bun run fetch:native --fmt"
    exit 1
```

Note the ordering: the upload is its own step, so the patch is always recorded even when the job
then fails on `main`. `--fmt` is therefore the documented local recovery path for a red `main`
`check` job. `clippy` warnings are **not** fatal during M0 bootstrap (no `-D warnings`); the
workspace declares `unwrap_used = "warn"` etc. in `[workspace.lints]`.

### §10.2 `web.yml`

Trigger: `push`/`pull_request` on TS paths. Jobs: `bun install --frozen-lockfile` →
`bun run typecheck` → `bun test` → `bun run build`. Uploads `web-build` (the vite `dist/` of both
apps) for the e2e job when it runs.

### §10.3 `image.yml`

On `main` only: build `deploy/Dockerfile.server` and `deploy/Dockerfile.gateway`, push to GHCR
(`ghcr.io/<owner>/monaca-server:<sha>` and `…/monaca-gateway:<sha>`), tags `<sha>` + `latest`.

### §10.4 `deploy-dev.yml`

On `main` after `image.yml` succeeds: SSH + `docker compose` on a VPS. When
`secrets.DEPLOY_HOST` (or any of `DEPLOY_USER`, `DEPLOY_SSH_KEY`) is absent the job exits 0
having done nothing — mode B depends on this workflow having run at least once.

### §10.5 Artifact names and destinations (contract with `fetch:native`)

| artifact name | contents | `fetch:native` destination |
|---|---|---|
| `server-x86_64-pc-windows-msvc` | `monaca-server.exe` | `.monaca/bin/monaca-server.exe` |
| `server-x86_64-unknown-linux-gnu` | `monaca-server` | `.monaca/bin/monaca-server` |
| `binding-x86_64-pc-windows-msvc` | `monaca-core.win32-x64-msvc.node` | `packages/core/` |
| `binding-x86_64-unknown-linux-gnu` | `monaca-core.linux-x64-gnu.node` | `packages/core/` |
| `codegen` | `index.d.ts`, `openapi.json`, `events/*.json` | `packages/core/index.d.ts`, `spec/openapi.json`, `spec/events/` |
| `rustfmt-patch` | `rustfmt.patch` | applied in place with `--fmt`, deleted afterwards |
| `e2e-report` | `skeleton.json`, `playwright-report/` | `.monaca/reports/` |

`fetch:native` fails loudly when an artifact is missing rather than leaving a stale binary.

### §10.6 Drift check

`codegen` compares its output with the committed files. During bootstrap — until the first
generated copy is committed — a difference is a **warning** on every ref; afterwards it **fails**
the job on `main` and warns on branches (same policy as rustfmt). Files compared:

* `packages/core/index.d.ts` — generated napi declarations vs. the committed file. The
  committed file must be napi's typedef output **as-is**; the hand-written placeholder shipped at
  bootstrap is replaced wholesale by the first codegen run, so review that first diff once
  instead of "fixing" it toward the placeholder.
* `spec/openapi.json` — generated OpenAPI vs. the committed file.
* `spec/events/*.json` — generated event schemas vs. the committed files.
* `.env.example` — every variable the code reads (a `grep`-based completeness check) must appear.

`bun test` in `web.yml` includes the differential test of native verification against `jose`
(plan §13): both must accept and reject the same tokens.

## §12 M0 acceptance (the `e2e:skeleton` contract)

`bun run e2e:skeleton --base-url <url>` implements plan §13 as executable steps. It is the same
script in all three modes and in CI; `<url>` is `http://localhost:8080`, the remote dev gateway,
or the CI server. Every step prints one JSON line to stdout and the whole run is written to
`.monaca/reports/skeleton.json`. Exit code is non-zero on the first failure.

| # | step | assertion |
|---|---|---|
| 1 | health | `GET {base}/healthz` → 200, `status == "ok"` |
| 2 | setup | `POST /v1/accounts` (email `agent-<runid>@demo.localhost`); `POST /v1/orgs/acme/members`; `POST /v1/orgs/acme/agents`; `POST /v1/orgs/acme/agents/{id}/keys` with a locally generated ES256 public JWK; `POST /v1/orgs/acme/grants` with `scopes=["tools:read"]`, `resource="{base}/mcp/demo"` |
| 3 | token grant | `POST /t/demo/oauth2/token` with `grant_type=client_credentials`, `private_key_jwt` assertion signed by the agent's private key, `resource={base}/mcp/demo`, `scope=tools:read`, `authorization_details=[{"type":"monaca_grant","grant_id":"grt_…"}]` → 200; decode the token: `act.sub == agt_…`, `scope == ["tools:read"]`, `exp - iat == 300`, `sub == acc_…` |
| 3b | over-request denied | same request with `scope=tools:write` → 400 `{"error":"invalid_scope"}` |
| 4 | allowed tool | MCP `tools/call` `list_notes` with the token → success |
| 4b | denied tool | MCP `tools/call` `delete_note` → 403, `WWW-Authenticate` contains `error="insufficient_scope"` and `scope="tools:write"` |
| 5 | audit chain | `GET /v1/orgs/acme/audit?grant_id=grt_…` shows `account → grant → agent → token(jti) → tool`; `GET /v1/orgs/acme/audit/verify` → `{"valid":true}` |

Playwright additionally walks step 2 and step 5 through the console UI; its report is uploaded
as part of `e2e-report`. Rust-side acceptance (plan §13): `#[sqlx::test]` covers every query plus
tenant/org provisioning and cross-org denial; `proptest` covers attenuation monotonicity and
audit tamper detection; `bun test` covers native vs. `jose` verification (§10.6).
